The diagnosis: undertrained, not overfitting

The evaluation history from the latest run tells the story clearly:

PR-AUC climbed monotonically to the final step — it never peaked and declined. That is the signature of a model that ran out of training budget, not one that overfit. An overfitting model shows PR-AUC rising then falling while training loss keeps dropping. This one was still improving when training stopped.

Why 512 tokens scored worse than 256

Counterintuitive, but it is a scheduling artefact rather than a finding about context length.

Both runs used the same 2,349 optimizer steps. Step count is dataset_size ÷ batch_size × epochs — it does not change when you lengthen the sequence. So the 512-token run had exactly as many gradient updates to learn a harder problem: twice the tokens per example, more positions to attend over. It simply did not get there.

There is a second effect that makes this worth rerunning rather than extrapolating from the curve. The learning rate follows a linear decay to zero across the planned steps. By step 2349 the learning rate was essentially nil, so the final checkpoints were barely learning at all. Running more epochs does not merely append more of that flat tail — it stretches the entire schedule, giving the model far more time at a productive learning rate.

One point in the transformer's favour

At step 2000: precision 0.967 with only 2 false positives out of 1,702 legitimate ads. The TF-IDF baseline's best is 0.930 precision with 5.

PR-AUC averages performance across all thresholds, but this product does not operate at all thresholds. Concept paper §3.6 states that false positives against real companies are the expensive error, and step 3.2 selects the operating point from a precision target. The transformer appears able to reach a higher precision ceiling than TF-IDF — which may matter more for the product than the PR-AUC summary suggests.

This is one checkpoint and the comparison needs a consistent threshold rule, so it is not yet a conclusion. But it is a reason to measure properly at step 3.2 rather than discarding the transformer on PR-AUC alone.

3 — The Indonesian dataset: fix this first

Correction to revision 1 of this brief. An earlier version stated the Indonesian evaluation dataset "does not exist." That was wrong — written after checking only one of the two machines. It does exist, at eval/indonesian_holdout.jsonl, with 200 items and a clean validator run.

What's there

items         : 200 / 200 target
labels        : 72 scam, 128 legitimate (36.0% scam)
channels      : {'job_board': 123, 'whatsapp': 44, 'other': 33}
source types  : {'job_board': 110, 'community_report': 72,
                 'company_official': 10, 'glints': 5, 'media': 3}
looks good.

Target size met, and the 36% scam rate is almost exactly the 35% the spec asked for — deliberately legitimate-leaning so false positives, the expensive error, are what gets surfaced.

The problem: 43% of items are not job ads

86 of the 200 items are under 200 characters, and 85 of those are labelled legitimate. They look like this:

Driver • Cititrans • Kompetitif • SMA/SMK • 1–2 thn • Luar Jabodetabek
Staff Gudang • Roschel • Kompetitif • SMA/SMK • 0–2 thn • Jakarta Barat
Kasir • Andifa Vet Clinic • Kompetitif • SMA/SMK • 0–2 thn • Jakarta Selatan
Helper Mekanik • PT. Anugrah Vindo Abadi • Kompetitif • SMK • 1–2 thn • Bekasi

Those are job-board index rows — the one-line summary from a search results page, not the advertisement itself. Every scam item, by contrast, is a full forwarded WhatsApp message with a median length of 767 characters.

ClassMedian lengthMinMax
Legitimate125 chars701,289
Scam767 chars1852,478

Why this invalidates the evaluation

Text length ALONE as a scam detector on this holdout:
  PR-AUC   0.8847
  ROC-AUC  0.9355

Best single threshold rule: "text >= 500 chars => scam"
  F1 0.8082   precision 0.7973   recall 0.8194   (TP 59, FP 15, FN 13)
Counting characters scores PR-AUC 0.8847 on this dataset — higher than either trained transformer managed on EMSCAD. Any model evaluated here will post an impressive number that is substantially just measuring "is this text long?", and the score alone gives no way to tell the difference.

It also does not match the product's real input. A user pastes a job ad they received. Nobody will paste a 70-character index row into TELITI, so those items measure performance on input that never occurs in practice.

The good news — close, not broken

114 of the 200 items are already exactly right. The Glints entries and the longer job_board ones are proper full postings:

[id-holdout-0088] Pharos Indonesia • Medical Representative
Mempromosikan produk farmasi ke dokter, apotek, rumah sakit. Kerja
lapangan, target-oriented.
- Pria/Wanita, pendidikan minimal D3/S1
- Komunikatif dan berorientasi pada target
- Siap bekerja di lapangan ...

The fix: open each short entry's source_url, click through to the actual posting, and copy the full advertisement body instead of the summary line. Same items, same labels, same sources — only text changes. Roughly 85 entries.

Two smaller issues

Source perfectly predicts label

source_typeLegitimateScam
community_report072
job_board1100
company_official100
glints50
media30

Zero overlap. source_type is not fed to the model, so this is not leakage in the strict sense — but the two classes differ systematically in origin, and the length gap is one symptom of that. Worth remembering when interpreting whatever score comes out.

Zero Telegram items

The contact_messaging_only rule deliberately weights Telegram at 0.75 versus WhatsApp at 0.35, because in Indonesia WhatsApp is ordinary business communication while Telegram is not. That asymmetry is one of the more considered Indonesian-context decisions in the rule layer, and nothing in the holdout currently tests it. A handful of Telegram-channel scam items would fix that.

Set a stopping rule now, before running these. If neither experiment clears 0.8769, stop. "A fine-tuned multilingual transformer matches but does not beat a TF-IDF baseline on EMSCAD" is a legitimate, reportable result. Continuing to tune past that point is how a project ends up overfitting to its own validation split by hand — and the number stops meaning anything.

Compare against 0.8847, not against zero. That is what text length alone achieves on this holdout. If the model does not clearly exceed it, it has learned nothing beyond document length — and that must be reported, not smoothed over.

What this changes in the concept paper

§3.3 presents the transformer as the core AI contribution. There is now measured evidence from three runs that, on EMSCAD, it matches but does not beat a classical TF-IDF baseline. That needs stating plainly.

This is not a weakness in the write-up — it is a stronger methods section than an unsupported claim. And if the transformer does outperform on a properly constructed Indonesian holdout — plausible, since TF-IDF learned untransferable English tokens like subsea and below link — the contrast becomes the most interesting result in the paper rather than an awkward footnote.

Exact wording is drafted in docs/PAPER_REVISIONS.md and will be finalised once the experiments settle on a number.
